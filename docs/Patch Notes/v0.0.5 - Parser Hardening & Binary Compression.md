# v0.0.5 - Parser Hardening & Binary Compression

**Date:** 2026-09-02 · **Phase:** Phase 2 · **Harness:** 13/14 (fuzz turned green; slow_reader keeps the stalled-reader policy finding)
**Report:** [harness_report_v0.0.5.json](../harness_report_v0.0.5.json)

> Server parser hardened against hostile frames; movement traffic moved from ~190 B JSON to 9-byte binary frames.

## Changes
### Server (`serve_game.py`)
- Frame length cap: a header claiming more than 4 KB closes the socket immediately (no waiting for, or allocating, the claimed payload).
- Relay payload cap: text messages above 1 KB are dropped, never relayed (no amplification).
- Control frames (ping/pong/continuation) are consumed properly; before, their payload desynced the reader.
- Binary movement path: validates type byte and fixed 9-byte size, stamps the sender byte from the assigned slot, relays without parsing.

### Client (`global.gd`, `player.gd`)
- `encode_sync_pos` / `encode_projectile` build 9-byte little-endian packets: type, sender, x*10 and y*10 as s16, aim angle in 0.1° as u16, flag bits (facing, dash, shield, bear, egg). Projectiles carry a weapon id instead of a string.
- `_process` dispatches on `was_string_packet()`; binary packets are decoded into the same dictionaries the handlers always received, so `player.gd`'s receive side is untouched.
- Druid thorns are networked (they were local-only before).

### Harness (`tools/chaos_bots.py`)
- Bots send and decode the binary format; the oracle and schema are unchanged.
- Fuzz gained: JSON-in-binary, bad type byte, wrong length, sender spoof (stamping check), over-cap 5 KB frame (must close), 2 KB relay-cap message (must drop), lying 64 MB header (must close fast).

### Docs
- Patch Notes section (now this vault folder), CLAUDE.md rule 5, `bump_build.sh` warns when a version has no page.

# Tower Brawl - Claude Code Developer Rules

## Architecture Orientation
- **Engine**: Godot 4 (Exported for Web / HTML5)
- **Networking**: Custom WebSocket implementation (`WebSocketPeer` in Godot, `websocket-server` in Python). We do **NOT** use `ENetMultiplayerPeer` or Godot's High-Level Multiplayer API.
- **Server**: `serve_game.py` is the authoritative python backend tracking lobby state, active players, and match logic.
- **Client Root**: `scripts/global.gd` handles all network packet parsing and delegates state to the UI.
- **The new game (P1, since 2026-10-10)** lives in `bench/`, its own Godot project grown from the 8-player benchmark: `sim/` (the rules, no nodes), `server/game_server.gd` (headless Godot, seats, rounds, wss 8091), `client/` (the web page: lobby, HUD, twin sticks; P2: your fighter predicted in `predict.gd`, the arrows on your tick in `present.gd`, the clocks in `net.gd`). Check: `godot --headless --path bench --script res://tools/check_scripts.gd`. Build: `tools/v2_build.sh --title "..."` (the version in `bench/sim/proto.gd`, the page in `build/web/v2/`). The plan: `docs/reference/first-playable-plan.md`. The old game above is untouched until v0.2.0.

## Critical Rules for Claude
1. **SCENE FILES ARE TEXT: EDIT THEM, THEN RUN THE LOAD CHECK. NEVER EDIT BINARY FILES.** (Rule changed 2026-09-08 with the tower arena, v0.1.3.) A `.tscn` is plain text; edit it with care (unique `id=` per resource, `load_steps` = ext + sub resources + 1, node paths that scripts use with `$`). After every scene edit run `godot --headless --path . --script tools/check_scripts.gd -- --no-net`: it loads and instantiates every scene under `scenes/`, so a broken file fails there, not in the game. `bump_build.sh` runs the same check. Binary files (`.pck`, images, fonts) are never edited by hand.
2. **THE BROWSER CACHING BUG.** Godot's web exports aggressively cache `.pck` files in IndexedDB keyed by file name. If you modify GDScript, you MUST run `./bump_build.sh`. It compile-checks every script (with autoloads live, because `godot --check-only` cannot see `Global`), bumps `GAME_VERSION` in `scripts/global.gd` (v0.0.x format, single source of truth, mirrored into `serve_game.py`), exports, copies the pck to `index_<version>.pck`, and patches `mainPack` in the HTML. If you skip this, the user's browser will load the old code and your fixes will seem broken! The server rejects joins from a mismatched version, and the client prints a VERSION MISMATCH line to the browser console.
3. **DO NOT RELY ON `_process` FOR NETWORK STATE.** The UI is entirely event-driven using signals from `global.gd`. Do not add polling loops to UI scripts.
4. **SPECTATOR VS PLAYER.** The network heavily relies on the `Global.is_spectator` boolean. A client connects as a spectator and is only given a slot ID if they explicitly send a `request_join` packet and the server replies with `assign_id`.
5. **PATCH NOTES ON EVERY BUMP.** Each version has its own page in `docs/Patch Notes/` (named `vX.Y.Z - Short Title.md`), indexed newest-first in `docs/Changelog.md`. Run `./bump_build.sh --title "Short Title"`: it generates the page from `docs/patch_note_template.md` and inserts the Changelog wikilink; then fill in the page (summary, changes, metrics, harness result). Harness reports per build live in `docs/harness_report_<version>*.json`.
6. **NEW SESSION? READ THE FOUR KICKOFF FILES, IN THIS ORDER.** (1) `CLAUDE.md`, (2) `docs/PASSDOWN.md` (the frontier only: the tag, the harness line, the next step, the last two builds, the open backlog, the architecture as it is now; capped at about 8 000 bytes), (3) the newest page in `docs/Patch Notes/`, (4) `docs/Commands.md` (every command and console field; capped at about 5 000 bytes). About 20 000 bytes in all. Read on demand only: `head -12 docs/Changelog.md` for the build index, `docs/reference/` for a feature's deep dive (`deck`, `harness-deck-and-gate`, `tape`, `replay`, `critical-learnings`), `docs/archive/backlog/closed.md` for a closed backlog number, `docs/archive/playtests/` for old sheets, `docs/archive/passdown/` for the old full PASSDOWN. Backlog numbers are never reused. A backlog line is `N. **Title** — state — next action — wikilink`; the story (log lines, theories) lives in the patch page or the sheet, never in the backlog line.
7. **SPEAK PLAINLY, KEEP THE SPECIFICS.** Explain code, causes, and architecture in direct, simple words—like explaining across a desk. No corporate filler, academic throat-clearing, or conversational padding.
   Crucial: "Plain" never means vague or dumbed down. Always preserve exact identifiers, file paths, function/variable names, packet keys, numbers, and data schemas. State the cause, state the fix, name the file, give the numbers.
8. **WRAP UP AND ASK FOR `/clear` AT EVERY MILESTONE.** Do this when a build is exported, checked, committed and tagged (tree clean), when a roadmap phase or a test milestone ends (for example the step 5 playtest), or when the chat has gone past about 15–20 turns or is full of command-line debugging output. The reply must end with: (a) the trim step: in `docs/PASSDOWN.md` add the new build bullet (four lines at most, ending in its patch-page wikilink) and delete the third-newest, move closed backlog items to `docs/archive/backlog/closed.md` (number, closing version, one line, wikilink), move sheets whose verdict has been acted on to `docs/archive/playtests/` (a sheet with an unticked verdict stays in `docs/`), then run `wc -c docs/PASSDOWN.md docs/Commands.md` and say the two numbers; over 8 000 or 5 000 bytes, trim before the wrap ends; (b) a check that `docs/PASSDOWN.md` and `docs/Changelog.md` match `git status` and the tag; (c) a short plain-words summary of what was delivered (rule 7); (d) a complete, copy-pasteable Kick-off Prompt for a fresh session right after `/clear` that names the four kickoff files of rule 6 in order, and the same prompt saved to `kickoff.md` in the repo root (overwrite it; commit it on `beta`), because the user's copy and paste sometimes fails: then they type "Read kickoff.md and do what it says". Then recommend `/clear`.
9. **GIT: TWO BRANCHES, `main` AND `beta`. NO OTHERS.** (The user's call, 2026-10-10.) `main` is the proven game: what the laptop runs on family nights, and where the version tags live. `beta` is where every build is made. On `beta`, commit whenever a step is checked (a proof passed, a page is done), without asking, and say so in one line. A commit never includes `cloudflared` (a binary the user manages by hand) or any key. After each commit push both branches (`git push origin beta main`): GitHub is the backup, nothing more. `main` changes only on the user's word: after a playtest sheet says pass and the user says "ship it", run `git checkout main && git merge beta` (main catches up to beta), tag the version, deploy to the laptop (the deploy still asks), then `git checkout beta`. A quick fix for the family game goes on `main` first, then `git checkout beta && git merge main`. Never rewrite history: no force-push, no rebase, no amending a pushed commit. Kick-off prompts and docs say "branch beta" and nothing more about git: no `master`, no feature branches, no pull requests.
8b. **MID-TASK? RECOMMEND `/compact`, NOT `/clear`.** Do not let a session go stale from a full context in the middle of a job. If the task is UNFINISHED (the code does not pass the tests yet, or no commit is ready) but the chat has gone past about 20 turns or holds several big command outputs or test dumps: (a) do NOT suggest `/clear` (the tree is dirty or the work is half done); (b) recommend `/compact` to squeeze the old terminal history and keep the focus; (c) first state, in one or two lines, the current guess about the bug and the very next action, so the summary keeps the live thread.
